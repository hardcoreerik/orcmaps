# Performance

Status: **first host measurements exist. NOT ESP32-VALIDATED.**

All numbers below are from a Windows host (Visual Studio 2026, Release)
rendering the Springfield / 97477 PMTiles archive through the real
OrcMaps pipeline. They are relative cost distribution, not Tab5 results.

```
HOST PERFORMANCE — NOT ESP32 PERFORMANCE
```

## What was measured (2026-09-14)

Pack: `data/local/springfield-97477.pmtiles` (3,507,636 bytes, PMTiles v3,
MVT, gzip tiles, z0–15, 141 addressed tiles). Regenerated by
`tools/pack-builder/build_springfield_pack.ps1`.

Viewport: 1280×720, `tile_size_px=256`, center 44.0500°N, 123.0220°W,
style `orcsdr-dark`. Preview visible-tile enumeration is host scaffolding.

| Zoom | Present / attempted tiles | HOST frame ms | render-sum ms |
|---|---|---|---|
| 13 | 9 / 24 (pack smaller than viewport) | 17.2 | 3.2 |
| **14 (primary)** | 20 / 24 | **220.7** | 4.4 |
| 15 | 24 / 24 | 692.2 | 2.5 |

Per-tile HOST cost on a busy z14 downtown tile (`14/2593/5953`, 88,658
stored / 141,658 raw bytes, 2,496 features):

| Stage | HOST ms |
|---|---|
| `GetTile` | 0.03 |
| `DecompressPayload` | 0.61 |
| `DecodeMvtTile` | 2.21 |
| `TranslateMvtToFeatureTile` | 0.71 |
| `AssignFeatureKinds` | 0.03 |
| `RenderFeatureTile` | ~0.2 |

Decode + translate dominate. Render is cheap at 1px strokes. The z15
frame is slower because more source tiles are present and each still
allocates a FeatureTile, not because rasterization is expensive.

## Tile payload sizes (MEASURED, this pack only)

z14 sample, 20 present tiles around the preview center:

| | stored (gzip) | decompressed |
|---|---|---|
| min | 14,092 | 19,623 |
| median | 64,662 | 99,833 |
| max | 88,658 | 141,658 |

z15 sample (9 tiles at radius 1): stored 18,185–33,272, decompressed
26,510–51,754.

**Provisional ESP32 caller budget (not a core constant):** 512 KiB per
tile covers this pack’s max (~139 KiB) with margin. 1 MiB is a
comfortable first SD-path budget. Do not freeze a global OrcMaps limit
from this one city extract.

## FeatureTile expansion (MEASURED, approximate)

Busy z14 tile `14/2593/5953`:

- 2,496 features, 5,814 paths, 23,776 vertices
- 6,049 property keys, ~113 KB of owned strings
- approximate FeatureTile owned bytes: ~1.2 MiB
- vs 142 KB decompressed MVT (~8×)

The current `MvtTile` + `FeatureTile` deep copy is acceptable if the
engine keeps **one source tile** in RAM at a time (ESP32-P4 + PSRAM).
Holding a full 20-tile viewport of FeatureTiles would be ~20 MiB and
is not the intended embedded path. Layer-string duplication is real
(`layer` copied onto every feature) but not the first blocker.
