# Tab5 SD Hardware Benchmark Demo Design

## Goal

Turn the existing M5Stack Tab5 proof into a Tab5-optimized interactive OrcMaps
showcase with a reusable, example-only hardware benchmark harness underneath.
The user sees a clean map application; serial JSONL and numbered SD reports
provide comparable engineering evidence for later LilyGO T-Display-S3 and CYD
ports.

This checkpoint is SD-card-first. It does not embed a map in firmware, change
partitions, touch OrcSDR, implement another board, add networking, publish, or
merge.

## Preserved starting point

- Source branch: `codex/world-overview-build-measure`.
- Source commit: `ede9e94dddb6854e0095264e4f97329882aec596`.
- New branch: `codex/sd-hardware-benchmark-bench`.
- The Natural Earth z8 master and all measured z4-z8 outputs remain local and

## Two-layer architecture

### A. Reusable benchmark infrastructure

An example-only component under `examples/hardware-benchmark/` owns:

- canonical scenario definitions;
- the measured OrcMaps tile pipeline;
- cold/warm result structures;
- portable identity, tile, timing, memory, storage, build, and result fields;
- JSONL formatting with explicit `null` for unsupported measurements.

It accepts an existing `ByteSource`, `RenderTarget`, viewport, style, content
profile, a microsecond clock callback, and memory-snapshot callbacks. It has no
M5GFX, M5Unified, Tab5, LilyGO, CYD, LVGL, SDMMC, or display-controller types.
It calls the real OrcMaps path:

```
ByteSource -> PmTilesReader -> GetTile -> DecompressPayload -> DecodeMvtTile
           -> TranslateMvtToFeatureTile -> profile classification
           -> RenderFeatureTile -> RenderTarget
```

There is one pipeline implementation for normal demo redraws and automatic
benchmark scenarios. Instrumentation is enabled by supplied hooks rather than
a second renderer or decoder. Cold and warm runs are separate records; a warm
run repeats the pipeline with filesystem/cache state left warm but does not
pretend a decoded-tile cache exists.

Full-file SHA-256 verification and sequential SD reads remain in the board
example because they operate on mounted filesystem paths and ESP-IDF crypto/
storage APIs. Their results populate the shared schema.

### B. Tab5-optimized interactive demo

`examples/m5stack-tab5/` owns M5Unified initialization, the 1280x720 layout,
touch interpretation, SDMMC Slot 0, ESP32-P4 heap/PSRAM probes, M5GFX
`DisplayTarget`, understandable error screens, and report-file lifecycle.

The display flow is:

```
brief loading screen -> SD and pack verification -> world overview -> interaction
```

The map remains the dominant full-screen visual. A thin top overlay shows
`OrcMaps`, active pack, zoom, and SD state. Large bottom touch targets provide
`World`, `-`, `+`, `Springfield`, and `Info`. UI overlays are drawn after the
timed map frame so their cost does not contaminate renderer timing. The primary
style remains `orcsdr-dark`; `standard-light` is available from Info as a
secondary visual check.

Touch drag calls `orcmap::PanByPixels()` with the inverse gesture delta. `+` and
`-` call the existing anchor-aware or integer zoom controls. `World` resets to
the overview. `Springfield` jumps to the known regional center at z14. The
first version redraws after a completed drag or button action; it does not add
pinch recognition, kinetic scrolling, or a tile cache before baseline hardware
measurement.

## Local source selection and truthful limitations

Runtime JSON manifest discovery is not implemented. The demo therefore creates
two `PackManifest` records from the exact verified sidecar values compiled into
the example, validates them with `ValidatePackManifest()`, adds them to a
`PackCatalog`, computes current visible bounds, and calls `ResolvePack()`.
Archive paths remain installed state.

The Springfield extract covers only a small bounding box. A 1280x720 viewport
does not fit inside it at every zoom from z8 upward. The demo must not relax
coverage rules or render a partially covered source as though it were global.
The `Springfield` control makes the smallest truthful transition by jumping to
the proven z14 view where the regional pack is eligible. At an uncovered z8+
view, the UI reports `DETAIL NOT INSTALLED FOR THIS VIEW`; it never uses an
Internet fallback.

Attribution comes from the active manifest record. The Natural Earth overview
has no legally required attribution in its manifest; Info may show the local
courtesy credit `Made with Natural Earth`. The Springfield pack displays its
required `© OpenStreetMap contributors` text unobtrusively. One universal
hard-coded attribution string is prohibited.

## Canonical scenarios

Scenario definitions are screen-independent; only viewport width and height
come from the board.

| ID | Purpose | Pack | Center | Zoom | Style |
|---|---|---|---|---:|---|
| `world` | global overview | z7 world | `0.0, 0.0` | 0 | `orcsdr-dark` |
| `oregon` | Pacific Northwest/Oregon overview | z7 world | `46.0, -121.0` | 4 | `orcsdr-dark` |
| `springfield` | original detailed hardware proof | Springfield regional | `44.0500, -123.0220` | 14 | `orcsdr-dark` |

Normal interactive startup may use `FitBounds()` for a more useful full-world
presentation on the 1280x720 screen. That does not alter the fixed z0 automatic
benchmark scenario.

## Exact SD artifacts

The card layout is user-readable:

```
/orcmaps/world-overview.pmtiles
/orcmaps/springfield.pmtiles
```

Corresponding `.manifest.json` and `.sha256` files should be copied beside the
archives for audit/provisioning consistency, although runtime JSON discovery is
not yet implemented. Before either archive is used, firmware streams the file
through SHA-256 and compares it with the expected value taken from its verified
manifest.

## Report format

Serial is authoritative. Every record is one line prefixed
`ORCMAPS_BENCH_JSON ` followed by one JSON object. The same JSON lines are
written after measurement to the next unused
`/sd/orcmaps/orcmaps-benchmark-NNNN.jsonl`; existing reports are never
overwritten.

The run begins with an identity record and storage records, followed by cold
and warm scenario records. Fields include:

- identity: OrcMaps commit, bench version, board, MCU, display, flash, PSRAM,
  build configuration, ESP-IDF, graphics adapter, pack identity/hash/profile,
  style, center, and zoom;
- tiles: visible/present/missing, stored bytes, ByteSource bytes, representative
  compressed/decompressed bytes, and feature count;
- timings: app-to-SD, SD-to-open, PMTiles open, enumeration, lookup, inflate,
  decode, translate, classify, render, and complete frame;
- memory: internal and PSRAM before/minimum/largest observations;
- storage: bytes, block size, elapsed time, and decimal MB/s;
- build/result: application size, partition size/utilization when available,
  PASS/FAIL, error stage, and notes.

Unsupported values are JSON `null`, never zero or invented. JSON string output
is escaped and tested. Reports are written after timed rendering. Failure
records are emitted when possible before the normal-user error screen remains
visible.

## Benchmark mode and normal mode

Normal boot enters the interactive map. `Info` opens a small panel containing
pack/coordinates/style/attribution and a `Run Benchmarks` action. The automatic
mode runs SD throughput plus the three canonical scenarios, cold then warm,
using the same renderer function as interactive redraws. It shows only the
current scenario, PASS/FAIL, zoom, and major frame time, then returns to the map.

The first physical acceptance run exercises both layers:

1. boot into the world map;
2. pan and use `+`/`-`;
3. use `Springfield` to show regional z14 detail;
4. run the canonical benchmark action;
5. capture the complete serial JSONL and resulting numbered SD report.

## Measurement boundaries

- Application-start-to-SD includes board/display initialization before mount.
- PMTiles open is measured independently for each source.
- Stage totals aggregate all visible present tiles.
- ByteSource counts are captured by delta for each frame.
- Cold is the first scenario execution after source open; warm immediately
  repeats it without reboot or cache clearing.
- Heap minimum APIs may represent the lifetime minimum. The schema distinguishes
  lifetime minima from before/after snapshots and uses `null` when the platform
  cannot provide a scoped minimum.
- Status/UI drawing occurs after frame timing ends.
- Historical Springfield 4.4 s (previously 11.3 s) remains context only. A
  changed viewport, source verification, instrumentation, or UI flow must be
  disclosed before comparing results.

## Validation and evidence

Host tests cover canonical constants, profile dispatch, JSON escaping/nulls,
numbered-report selection, cold/warm labeling, and failure-stage output. Before
flashing is requested, run host C++ tests, Python tests, consumer build/tests,
documentation and provenance checks, world-overview independence checks,
whitespace checks, the Tab5 ESP-IDF build, and the firmware size report.

`docs/evidence/HARDWARE_BENCHMARK_TEST_BENCH.md` records commands, schema,
artifact identities, build/size status, exact SD preparation, flash/monitor
steps, expected serial markers, and explicit PREPARED / BUILT / HOST VERIFIED /
HARDWARE VERIFIED boundaries.

## Known first-test concern

The current renderer has no decoded/rendered tile cache. Springfield previously
took about 4.4 seconds for a full cold frame, so drag-release redraws may not yet
feel fluid at z14. This checkpoint measures that behavior instead of hiding it
with an unmeasured optimization. Any cache or incremental-pan work follows the
physical baseline as a separate change.
